3. **What stops and for how long.** Set B job B2 stops the trading worker and the staging API, installs M6, applies the targeted grant, and starts the API and then the trading worker. Expected gap on the normal path about 20 to 40 seconds (P3 a02 API gap 19.0 seconds plus one more unit; design F12) [D2]. During the gap the staging UI does not answer. Webhooks and alerts that arrive during the gap are refused, not queued; an alert is lost unless its sender retries. Signals already queued before the gap run after the worker start. This is the first time an S6 job stops a running trading worker (REPIN-2 line 895).
4. **What can go wrong (failure outcomes).** If a step fails, the job restarts only the units whose stop it proved, the API and then the trading worker; a unit whose stop was not proved, or never sent, gets no start in this run, and Root reviews before RS under its own GO (rulings SB29 item 3, SB30 item 1). If a start fails, that unit can stay down until Root runs the restart-only job RS under its own GO (section 7.2); the whole staging UI is down while the API is down. If the job itself is terminated (for example by its host time bound), it sends no further command, so a unit it had stopped stays down until RS (SETB-R11). If the failure comes after M6 is installed but before the grant, M6 can stay installed without the grant, and the owner view still answers 503 (safe; nothing is declared) until the rollback RB, which is then the only next step; a later set B then needs a new set B job B0, a new set B job B1 if the B1 dump is older than 72 hours, and a new set B job B2 (ruling SB9 OQ-16). In the unlikely case that the runtime role already holds non-exact privileges on the new M6 objects, the job does not try to fix them inside the window: it restarts the units and stops for Root, and the undo is RB (SETB-R8).
5. **What keeps running.** The market stream and the fallback collector service and timer keep running and get no command [D6]. The research worker stays stopped. Production is out of scope and is identity-checked before and after.
6. **What does not happen.** No code tree, drop-in layer, environment file, flag or manager reload changes. The API stays on pin `75c7a5b` through the REPIN-2 layer; the trading worker stays on `ba1a433`. No declaration is made [D3].
7. **The jobs and GOs.** On the normal path you give three GOs: GO-B0 (read-only check), GO-B1 (fresh backup and a test restore on a throwaway copy) [D4] and GO-B2 (the offline window), and then you do the browser check. Only if a declaration row exists: GO-RBX (export) and then GO-RBC (undo with the export confirmation) [D7].
