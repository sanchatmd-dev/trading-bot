# Staging prototype delivery plan — 2026-10-01

The owner requests an accessible staging prototype first, followed by a working
six-step journey. This plan narrows the first delivery; it does not declare
unfinished engineering accepted or replace the governing Roadmap gates.
The current request is planning and handoff to Claude. No runtime work is
performed by this documentation checkpoint.

## Scope and delivery order

Use one owner, one Bot and one supported, inspectable Pine indicator on
BINANCE:BTCUSDT Spot 1m. Keep the current 10,000-bar limit including warm-up.
TradingView supplies real alerts; order execution remains Paper with reduce-only
exits. Multi-Pine, paid beta, Live, expanded capacity and automated apply are
outside this prototype. Existing downtime and staging deployment authorization
remain valid; technical acceptance and recovery gates still apply.

Deliver two clearly distinguished checkpoints:

1. **P0: visible staging preview.** Provide a verified authenticated staging URL,
   a short walkthrough and a six-step progress view. Reuse accepted chatbot,
   Bridge and PF-1 functionality. Expose available real functionality and explain
   unavailable steps with their next dependency. Historical results may be shown
   with their original run identity. Fixtures, if needed for an unimplemented
   screen, must be labelled and isolated from real results and actionable values.
   This is an early preview, not six-step acceptance.
2. **P1: six-step functional prototype.** Complete the acceptance matrix below
   on a pinned staging release with real AI generation, TradingView transport,
   Paper accounting, bounded optimization and durable library records. The result
   may legitimately be “no qualified candidate”; a profitable winner is not a
   deployment criterion and must not be fabricated.

## TradingView, data and browser work

- Use exchange OHLCV for the supported historical evaluator. Continuous chart UI
  scraping is not the data backbone.
- Reuse existing immutable parity evidence only when source, effective inputs,
  evaluator semantics and market/timeframe match. Changed or unsupported inputs
  require fresh scoped parity/repaint evidence. CSV signal replay does not create
  evaluator support for optimizing arbitrary source inputs; optional CSV support
  itself remains pending where not implemented.
- Root owns the browser session: Pine compile, ten-input inspection, chart/source
  binding, alert creation/replacement and end-to-end UI checks. Read the relevant
  browser/computer-use skill before use. Prefer supported browser automation;
  native computer use is only needed for otherwise inaccessible UI and only if
  available. Login/MFA or unavailable tools may require owner participation.
- Server deploy, backfill, scheduler, optimizer and persistence use the reviewed
  operational tools, APIs and database checks. No TradingView MCP is required.

actions, independent acceptance, job ID where applicable, budget, logs and
stop/recovery details using the project task template. Proposed roles above are
not active dispatches. No worker approves its own result; one Git operator and
one server operations coordinator at a time.

Record actual engineering time separately from machine waits and market waits.

acceptance, estimate remaining P1 packets from observed work and current defects.

estimate and is not reduced by agent count. Natural signals and qualified
research outcomes have no guaranteed deadline.

Management, review README/Context, commit only reviewed exact paths and push the
authorized branch. Commit, deployment and acceptance remain separate facts.
