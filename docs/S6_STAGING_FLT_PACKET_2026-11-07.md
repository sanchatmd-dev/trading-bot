## 6. Phases run by the tool

These are the phases of the L11 packet r2 section 3 with Root's amendments, in run order. Each write runs in its own READ COMMITTED transaction, with lock order owner, then signal, then Bot.

- **E0 (read only).** The staging health answer (200, ok, mode PAPER_ONLY) and a database read (server version, schema version 14); R-BY, the host read of the six file hashes in both trees; both owners and Bots exist and are ACTIVE, each Bot is a child BOT user and is STOPPED; no other QUEUED or PROCESSING signal and no earlier run signal; the runtime role is not a superuser and holds the needed table grants; a fresh worker heartbeat (at most 15 s old) and the hashed set of execution worker ids; the before accounting snapshot. The read session proves that it refuses a write. Any miss is a stop with no write effect.
- **R-OR (read only, context).** The runtime role cannot leave `origin`. A stopped read stays UNKNOWN and the job goes on.
- **E1.** One malformed signal for Bot A. **R-BR** then reads the bounded rejection: `EXECUTION_FAULT: OTHER`, one fault row with attempts 3, one outbox row, accounting unchanged, and at least 6000 ms from receipt to the fault row.
- **E3.** One malformed signal each for Bot A and Bot B in one transaction. **R-SH (hold)** at 30 s or more: both QUEUED, two suspension rows (key `OTHER:SyntaxError`, owner count 2), no fault or outbox row.
- **E5 (option A).** One operator UPDATE replaces Bot B's payload with a well-formed payload. **R-SH (after):** B is rejected by the product path (`Bot is stopped: no signals accepted`), A is rejected by the bound, accounting unchanged.
- **E6.** A lock session sets its idle-in-transaction backstop (21 s), takes FOR NO KEY UPDATE on Bot A's child user row, and a second session inserts one well-formed signal. The lock is held for 17 s to 20 s. **R-TF (hold)** at 16 s or more after the insert, with catalog waiter evidence; **R-TF (after)** after the release: the product rejection with zero fault rows. A hold read that cannot finish before the cap is dropped and R-TF becomes a stop (UNKNOWN), never a fail.
- **C (every end path).** C0 releases the E6 lock session if this process still holds it, and ends any stray session of this run's own tool: only sessions whose application name is one of this run's three tool session names and whose role is the runtime role, never a worker backend. C1 is one READ COMMITTED transaction with a 30 s bound: it locks both test owner rows and sets still-QUEUED run-scoped signals of the two test Bots to REJECTED with `FLT_CLEANUP`. It writes no audit, outbox, cash, fill, lot or fence row. C2 reads, read only: zero run-scoped QUEUED signals, no live tool session or lock, the after accounting snapshot equal to the before snapshot, and the heartbeat and worker set. On the pass path C1 updates 0 rows.

### 7.1 Before the run

1. **Admission by Root.** Root confirms every item of section 2, including the four ids filled in the private binding input and the attached local check result (section 2 item 9), holds the owner's typed GO-FLT-1 line, reads usage, and dispatches the operations worker with the attempt id `a01` and a new run nonce (6 to 16 lowercase letters and digits; not private). 2. **Fresh health read.** The operations worker takes the bounded health read of section 2 item 2. A miss ends the attempt here with no tool run. Root records it as a stop (`FLT_STOP_HEALTH`, before the tool).
3. **Job record folder.** The operations worker creates one new protected job record folder on the staging host, outside both deployed trees. It is unique per attempt and refused if it already exists. It holds the runner output (`out`), the receipts, `progress.json` and `result.json`, and nothing else of the job.
4. **Job-private tool folder (SB197 item 3, set B section 4.5 form).** The operations worker creates one job-private sibling folder for the tool. 6. **pg resolution without editing the deployed tree (SB190 item 3).** The tool imports the `pg` package. ### 7.2 The run

9. **Detached runner under a hard time bound.** The runner runs detached from the SSH session in the set B runner form (SETB-R9): a transient user manager unit with a removing collect mode, control-group kill mode, a runtime maximum equal to the host bound H, a stop timeout, and a marker argument that holds no private value. The login manager's logout-kill setting is checked first, and the job does not start if that setting is on or unknown. Root confirmed these values in SB197 item 1:
   - the tool's own in-run limit is 360 s in total, with fixed per-phase limits and a 30 s C1 bound;
   - host bound H = 600 s;
   - the transient unit's stop timeout is 120 s;
   - the lost-receipt wait is H plus 135 s.
10. **C-phase bound against the 120 s stop timeout.** After a termination, the runner first lets the statement in flight finish under its own timeout (5 s connect, 10 s per statement in a write transaction, 15 s per read statement); an aborted wait ends at once. Phase C then runs:
    - C0: at most 15 s (5 s connect, then the 10 s session statement timeout of the binding);
    - C1: at most 35 s (5 s connect, then the 30 s hard bound, inside which the UPDATE commits or the transaction rolls back);
    - C2: read only, 5 s connect and a 15 s timeout per statement for about 17 small count reads, which ran in milliseconds in the rehearsal; C2 has no tighter joint hard bound.
    The one write after a termination, C1, therefore ends at most 50 s after phase C starts. With the 120 s stop timeout, C1 ends before any kill unless the statements of the step in flight together take more than 70 s, which needs several statements of one step to each run close to their timeout. A kill during C2 cannot undo C1. If a kill comes before C1 commits, the C1 transaction rolls back when its socket closes, and the hard-kill path of section 7.3 runs.
11. **Command.** `node flt-runner.mjs --binding <binding file> --run <nonce> --out <record folder>/out`. The runner writes one receipt per phase, `progress.json` and, at its end, `result.json`.
12. **Watching.** The operations worker reads `progress.json`, read only. It sends the runner no command, except a termination signal when the owner or Root asks to stop.

### 7.3 Termination form (SETB-R11, relaxed for C1 alone)

- **Caught termination.** A caught signal (interrupt, terminate or hang-up), a runner terminate message or the tool's own time limit ends the effect sequence. Reaching the host bound H is also a caught termination: the manager then sends the stop signal, which the runner catches. The runner sends no further effect except phase C. It runs C0, C1 and C2 in process, then evaluates. The verdict is `FLT_STOP_TERMINATED` or `FLT_STOP_TIMEOUT`, and C1 may close the run's QUEUED signals. C1 is the one write allowed after a termination: one READ COMMITTED transaction on run-scoped rows of the two test Bots, with a 30 s bound, starting nothing and giving no unit command.
- **Hard kill.** Of the kills that the unit manager sends, only a kill after the 120 s stop timeout writes no end code. Reaching H alone does not: it sends the caught stop signal, and phase C runs in process. The lost-receipt wait (H plus 135 s, 735 s) is longer than H plus the stop timeout (720 s), so any such kill has happened before the wait ends. An outside kill, for example by the OOM killer or a host restart, can come at any time; it also writes no end code and takes the same path through section 7.4 item 13. After a kill the operating system closes the runner's sockets, PostgreSQL ends its sessions and rolls back any open transaction, and the E6 lock is released (the 21 s server backstop also applies). After the lost-receipt wait (H plus 135 s), the operations worker reads the progress record and runs `flt-cleanup.mjs` once, with the E0 receipt file if it exists.
- **Standalone cleanup form.** The standalone cleanup always runs detached in the same transient form as the runner: a transient user manager unit with a removing collect mode, control-group kill mode, runtime maximum H, stop timeout 120 s and a marker argument with no private value, after the same logout-kill check. It writes its C receipt to the job record folder. A kill of the standalone cleanup before C1 commits rolls back C1, because C1 is one transaction.
- **Cleanup failure.** A cleanup failure is a C receipt of status STOP or a missing C receipt (verdict `FLT_STOP_CLEANUP` with detail `c_failed`, `c_missing` or `c2`), in process or standalone. The operations worker reports to Root and the owner at once and sends nothing further.
- **Recovery authority (SB197 item 5, SB199 items 2 and 4, Root's r4 decision 1).** Under GO-FLT-1, Root may order up to two more standalone cleanup runs, each in the standalone cleanup form and each one at a time. Each one starts no later than notAfter plus 105 min, so that it and every removal end before notAfter plus 120 min. For each such run the binding file may be re-created under section 5. Once a recovery cleanup is confirmed, the exact-path removals of section 7.4 item 15 follow, also before notAfter plus 120 min. The exact-path removal of the binding file is always required, needs no further GO and is exempt from that limit (section 5). No other step runs under this recovery authority. If cleanup still cannot complete, Root stops, asks the owner for a cleanup-only GO, and tells the owner privately which test owners stay held. The owner can stop staging at any time. No further FLT attempt runs until Root has reviewed a completed cleanup.

13. **End cases.**

16. **No other unit command at any point.** The job does not stop, start, restart or reset any staging unit. Its only unit actions are the start of its own transient runner and standalone cleanup units and a termination signal to them. After the job, the worker's in-memory fault state clears through commits and terminal writes, and the evidence for signals closed by C1 ages out within 60 s.

## 8. Stop and fail semantics

- **`FLT_PASS`** needs every check to pass (R-BR, R-SH hold, R-SH after, R-TF hold, R-TF after), every precondition met (E0 OK, R-BY OK, worker set recorded), cleanup confirmed with C1 at 0 rows, and the worker alive and unchanged at C2.
- **`FLT_STOP_<reason>` leaves T UNKNOWN.** A stop never maps to a fail. The stop set, which GO-FLT-1 names: `HEALTH`, `PIN`, `ACCOUNT_STATE`, `BOT_NOT_CHILD`, `BOT_STATE`, `QUEUE`, `GRANT`, `ROLE`, `HEARTBEAT`, `WORKER_CHANGED`, `READ_ONLY`, `BINDING`, `E0_RECEIPT`, `PHASE`, `TIMEOUT`, `TERMINATED`, `TOOL`, `CLEANUP`, `INCOMPLETE` and `UNKNOWN_<check>`. Worker continuity is judged before any check: a stale heartbeat, a gap, a restarted or added worker, or a changed target is a stop, never a fail.
- **`FLT_FAIL_<check>` does not set T to 0 by itself (SB190 item 2, SB197 item 6).** Root first reviews the run's audit rows and receipts. Known residual causes are a third owner whose signal fails with the same key `OTHER:SyntaxError` inside the 60 s window, and the narrow stall window of the R-SH hold read. The F-5 aggregate read of other tenants' recent faults stays declined, so this review covers the third-owner case. If Root finds an environment cause, the result counts as UNKNOWN. Only a Root-confirmed product failure with every precondition met makes T 0 for F03-03. Root records it at the next scorecard. The evaluator's `credit_hint` text is advisory only and never sets T (section 4). If the review needs a database read beyond the receipts, that read needs its own owner GO.
- **Cleanup dominates.** A missing, failed or unconfirmed cleanup (detail `c_missing`, `c_failed` or `c2`) gives `FLT_STOP_CLEANUP` whatever the checks showed, and the recovery rule of section 7.3 applies. The detail `c1_rows` is different: cleanup was confirmed, and the stop only records that C1 closed run-scoped rows on a would-be pass path.
- **R-OR** is context only. Its result never changes the verdict.
