### 4.3 Job m1: effects, in order

No daemon reload at any point. Control verbs only on the three market units. The record directory is created in the dedicated protected backup directory, with a progress record and a result file (labels and counts only).

1. **Start the stream.** No reset-failed before the start (the gate refuses a failed unit). Ready when active and running with a new main process and invocation, configuration digest equal to the gate value, stable for 3 seconds with the restart count unchanged.
2. **Catch-up and live proof** (read only, a fresh transaction per poll). Caught up when the latest stored bar is at most 180 seconds old (age measured from the bar's close, here and below), within 120 seconds plus 30 seconds per gap page; contiguous (row count equals the elapsed minutes); live (at least one new row whose provenance starts with `wss://` within 150 seconds after catch-up). No progress inside the bound means a venue refusal, a host clock behind the venue, or a crash; the tool rolls back and the record shows the stream journal kind counts.
3. **Run the collector service once**, started without blocking and proved by state within 300 seconds: new invocation, new start time, back to inactive and dead with success status. A run still active at 300 seconds, a failed state or a non-zero status is a failure. The service runs before the timer because a timer relative to the service's last activation has no next elapse until the service has run.
4. **Start the collector timer.** Ready when active (waiting) with a next elapse set on either clock within 15 seconds, then stable for 3 seconds. With a calendar trigger, the first scheduled run (realtime next elapse) must fall within 900 seconds after the timer is ready; otherwise the in-run rollback runs (ruling D38).
5. **Immediate checks** (read only): the three units as left; the pair unchanged (same processes and restart counts); research worker stopped; no unit needing a reload; empty job list, except the collector service's own start job while a timer-started run is in progress, with the timer then reading running (recorded; ruling D36); production identity equal to the baseline; loopback API health equal to the gate answer; latest bar at most 180 seconds old; stream journal kind counts (a fixed kind list, counts only); collector summary-line count (0 or 1); session counts by name and the Paper counter reading as records.
6. **In-run rollback.** Any failure in steps 1 to 4 stops the collector timer, then the collector service, then the stream, each to inactive: stop proof with the failed allowance, then reset-failed on that unit only when it is proven stopped in the failed state, then a second stop proof that requires inactive. A collector service or timer found mid-run is stopped by the same sequence. Units never started are proved stopped only; a unit that reads inactive with a queued start job is stopped like a running one. At the end of the rollback no job of a market unit may remain. Verdict `P4M_STOP_ROLLED_BACK` with the failing code and each unit's label. Stored bars stay (append-only public market data; no tool deletes). A failed proof, a failed reset-failed or a unit not inactive afterwards ends `P4M_STOP_HALF`; Root reports and the owner decides on GO-RM.
7. **After all three are ready**, a failed immediate check does not roll back: verdict `P4M_STOP_AFTER_READY` with the code, units left running; Root reports and the owner decides on GO-RM. A production-identity difference is reported per unit and never triggers a control verb.

Verdict `P4M_PASS` only when every step and check passes.

### 4.4 Job m6: delayed read-only check

One read-only job in a separate session under the same owner GO. Root dispatches it inside a window computed from the m1 record: earliest = timer ready + time to the first scheduled run (the smallest monotonic span, or, with a calendar trigger, the time to the realtime next elapse, whichever is smaller) + timer accuracy + randomized delay + 300 seconds (collector run bound) + 10 seconds (670 seconds with a five-minute monotonic trigger, one-minute accuracy and no randomized delay; about 1211 seconds on this host (accuracy 1 second, no randomized delay) with a calendar trigger whose first run is 900 seconds away); latest = earliest + 1200 seconds.

## 9. Residual risks and unknowns

The risks of main packet section 11 apply. Added by this packet:

- **Host code of the market writers.** The host copy's revision is unknown today. The gate stops unless every code file equals a known repository version, so a passing run executes code whose network endpoints are known (public, keyless Binance market data). A copy that predates the repository history, or was edited on the host, stops P4M before any effect. The packages `pg` and `decimal.js` are checked for presence only, with the version recorded, not hashed.
- **Database target.** G12 proves the socket, port and database of each writer's connection string before any write; the live proof confirms it from the data side. A writer that opens a second connection elsewhere is not excluded, but the scripts open one. A TCP or client-key-filled target stops P4M.
- **Temporary code location.** Age-based cleanup could remove files between the gate and a later restart; a missing file stops before any effect. A restart by systemd after a cleanup would fail and leave the unit failed or restarting.
- **Calendar timer.** With a calendar trigger, the time of the first scheduled run comes from systemd's next-elapse value, not from a span the tool reads; the calendar text is never read out, so no tool bounds the period of later runs, and the m6 check proves only that one timer-started run happened. If the host calendar puts the first run more than 15 minutes after readiness, m1 rolls back after the stream start, catch-up and collector run (`M_TIMER_FIRST_RUN`); Root cannot time the start, because the calendar text stays on the host.
- **Unknown systemd formats.** A systemd major outside the Root-checked set, or a value outside the derived formats, stops before any effect (m1, RM) or ends the effect with a format code; it never passes on a guess. The stopped-timer value forms are unobserved on this host; the first m1 gate is the first real observation.
- **Venue changes and host clock.** A tick or step change makes the stream exit; a missing venue minute stops catch-up; a host clock behind the venue gives stored-by-REST rows, so the live proof fails and m1 rolls back although the stream works. All fail safe; stored bars stay.
- **Silent failure after m6.** No tool watches the stream after m6. A persistent failure loops on reconnect and bars go stale until someone looks; nothing alerts.
- **Failed timer run after a pass.** One failed collector run leaves the service failed until the next good run; an RX gate in that window refuses, and RM clears it. R4 and R4H need RM anyway.
- **Paper rows on the pin.** Fresh bars let Bridge alerts create signals and fills; then R4 refuses by default and only a forward fix, an accepting R4 or RX remain (main packet section 8).
- **Backlog load and later session waits.** Catch-up is one transaction per bar for the stream and one per page for the collector on the shared host. While the writers run, any tool that waits for zero client sessions never succeeds, and a foreign-session check refuses if the writers' connection sets an application name outside the runtime names.
- **RX collector start (F2).** An RX after P4M may end `RX_RESTART_FAILED` at the collector restart after a successful data restore; the data restore would be done and the collector left stopped.
- **P5a cannot see the panel.** The owner's browser check after Root's report is the only functional proof on staging.
- **Memory.** One QR-2 computation adds up to about 300 MB on a host shared with production (two CPUs, 7.8 GiB); the gate checks the API unit's own limits and host memory, not parent slice limits.
- **Shared manager reload.** The manager reload (P5a, R5a, any unwind) is shared with production; D30 normalises the known production status tail, but any other reload-visible change of a production unit stops before the API start (unwind) or after readiness (API left running). A P5a job can run two reloads. A pending job of any unit on the shared manager at the reload gate can stop P5a or R5a with the staging API stopped (fail safe).
- **Environment scope.** P5a and R5a no longer read the database key or the PostgreSQL client keys, so a change of those keys in an environment file since P4 is not seen by the gate. A broken value makes the restarted API fail readiness, which the unwind handles; a working value that points to another database is not seen.
- **R5a end states.** Three recovery states have no admitting tool in this packet and need an owner decision, including the state after a production-identity difference in the unwind.
- **P5a terminated after the API stop.** A termination or deadline after the proved stop leaves the staging API stopped on the P4 configuration (`P5A_STOP_UNWOUND`). Neither R5a nor a new P5a admits that state; R4, R4H or RX does, each under its own GO.
- **R5a states that a new R5a refuses.** A row E4 run that fails again, an R5a start in row E1 that ends failed, and a P5a layer write that created no file followed by a failed unwind start each spend the GO of the next R5a at its host gate; R4, R4H or RX admits them.
- **Market units in a transition.** A stream that is starting, or a market unit that is stopping, reads as unknown: RM refuses before any effect and the m1 rollback ends half; no tool of this packet stops a stream stuck while starting. RM trusts the bound unit map and does not re-check the units' configuration.
- **Dependency links of the staging API** are not gated by P5a or R5a. The S6-API-SERVICE-START-1 record of 24 October counted, for the staging API unit, no bind, failure or success link, two requires entries and one conflicts entry (names not recorded).
- **Baseline after P5a.** Until Root rules whether a reviewed P5a or R5a production read is a valid baseline source for R4, R4H and RX, a production change after P5a leaves them without a usable baseline.
- **Webhook gaps.** Staging alerts and webhooks are not served during each API gap (P5a, R5a, any unwind): bounds 280 and 345 seconds, expected about 7 to 13 seconds. P4M and RM have no API gap.
- **Reboot.** The staging API unit does not start at boot; a reboot after P5a stops the pinned API, and the P5a layer applies at the next manual start.
- **Journal line cap at the P5a gate.** The P5a fresh gate reads the staging API and trading-worker journals since the switch; if a read reaches the line cap, P5a stops before any effect and the GO is spent.
- **Real local process termination** on Windows stays unqualified; only simulated in tools.
