# Legacy optimize transaction design — 2026-10-15

Verdict: recommend narrow containment first: an absolute upstream deadline below the 20s idle transaction limit, complete Promise settlement, and scoped post-submission error semantics. Do not raise production DB timeouts. Moving submission outside the transaction is structurally stronger, but needs an explicit executor-mode concurrency contract and durable-intent decision before implementation. Design only; root decides. Implementation waits valid CX3 integration (INT-R7).

## Source evidence and actionable risks

Paths below relative to frozen `.qa-local/int-r6/`.

1. **High correctness risk: external work outlives idle transaction.** `src/postgres/server.js:164` inserts RUNNING; `:169-180` waits for upstream before next SQL at `:184`/`:196`. `:171` specifies 30000ms socket timeout, not an absolute completion deadline. A response emitting chunks can keep extending activity. This conflicts with the supplied 20000ms idle transaction setting. DB rollback cannot undo submission (`:167`). A successful upstream result can therefore fail persistence and lose the inserted run row. Existing regression asserts that loss after injected SQL failure: `test/postgres/quant-bridge-sqlstate.test.mjs:67`.

2. **Medium correctness risk: ambiguous submission receives retry advice.** Dispatcher excludes legacy paths and checks `phase2External` before automatic retries (`src/postgres/request-dispatch.js:25`, `:84`), correctly limiting the handler to one outbound attempt. Its error mapper nevertheless sends `RETRY_TRANSACTION` / “Concurrent update; retry the request” after external work (`:108`). Test pins that behavior at `test/postgres/quant-bridge-sqlstate.test.mjs:58-60`. Client retry can submit another optimization. Change only the optimize post-attempt branch; retain normal transaction-conflict semantics elsewhere.

3. **Medium correctness risk: incomplete response settlement.** `src/postgres/server.js:174-178` handles response data/end and request error/timeout, but lacks response error/aborted/premature-close handlers. Oversized response explicitly destroys the response. Every such branch must settle the outer Promise once and clear the absolute timer. Otherwise an upstream failure may leave the route pending or emit an unhandled response error.

## Recommended bounded coder contract

Keep existing transaction boundary for this first slice. Apply the new deadline/outcome behavior specifically to `/api/quant/optimize`; do not alter backtest, health, risk-preview, optimizer parameters, holdout, Risk Manager, or managed-job policy.

- Preserve dispatcher order: request limits, origin/CSRF checks, body preload, session preparation (`request-dispatch.js:73-77`), then transactional session/permission checks (`server.js:255-258`), executor-mode denial (`:151-154`), ownership (`:162`), and run insertion. An admission or INSERT failure causes zero outbound calls. Keep existing GET/POST admission unchanged; method-policy tightening is separate scope.
- Proposed fixed absolute upstream deadline: **10000ms**, starting immediately before request creation and covering connect, headers, complete body, and parsing. Keep/shorten inactivity timeout as a secondary bound. This leaves nominal 10000ms before the supplied idle limit for scheduling and cleanup; it is not a hard wall-clock guarantee under event-loop stalls. The total request can still spend time in subsequent SQL, governed separately by DB limits. Root must accept that formerly successful 10–30s responses will now return an uncertain outcome.
- Set the existing no-retry marker before creating the upstream request. Maintain request-local optimize state distinguishing no attempt, attempted with no complete valid response, and complete valid response received. Never clear attempted state after rejection. Do not use `oncePerRequest` for this guarantee: `request-dispatch.js:32-40` deliberately evicts rejected promises.
- Use one settlement function for success, request error, absolute deadline, response error/aborted/premature close, invalid JSON, and body-size overflow. Settle before destroying streams; retain error listeners and ignore late events. Clear timer on every terminal path. Timeout/abort stops local waiting, not the remote optimization.
- Retain at most one outbound attempt per incoming HTTP request. Exactly-once execution cannot be guaranteed without upstream idempotency. Duplicate incoming requests and process crashes remain outside this slice; do not add retry, idempotency, recovery workers, or an optimization campaign.
- Before submission, preserve existing authentication/admission/DB failure responses. After submission without a complete valid response, return a stable scoped error identifying **unknown submission outcome**, with no retry instruction or claim of cancellation/non-submission. Proposed 503/code `QUANT_SUBMISSION_OUTCOME_UNKNOWN`; exact API wording subject to root approval. Do not mark this transport uncertainty FAILED.
- After a valid upstream response but failed UPDATE/COMMIT, return a distinct scoped persistence error, e.g. 503/code `QUANT_RESULT_NOT_RECORDED`. Say submission occurred but result persistence was not confirmed; never return buffered success. Retain SQLSTATE propagation and one audit, including conservative handling of COMMIT ambiguity. Do not expose raw SQL or upstream transport internals.
- Keep existing COMPLETED/FAILED mapping for complete valid upstream responses. Preserve current transaction behavior: caught transport uncertainty can commit a RUNNING row; SQL failure can roll it back. This slice does **not** repair absent/orphaned run records or make RUNNING an assertion that upstream is still executing. Document that limitation explicitly.
- If the client disconnects before any outbound attempt, skip submission where detected. After an attempt starts, do not resubmit; finish bounded settlement/persistence even if no HTTP response can be delivered. A lost response never proves failure upstream.

Files for a future root-authorized coder: `src/postgres/server.js`, narrowly scoped optimize outcome mapping in `src/postgres/request-dispatch.js`, and tests listed below. No DB timeout, schema, optimizer, or managed executor change needed for containment.

## Alternative: split external work outside DB transaction

Sequence: short admission transaction authenticates/checks permission, ownership and executor mode, creates RUNNING intent and returns an immutable data-only descriptor; COMMIT must succeed before sending. Invoke external work only after `database.transaction` resolves, outside its AsyncLocalStorage transaction context. A second short transaction persists the complete result using captured run/user/bot identity. Buffer HTTP success until that second COMMIT. Never reuse a closed transaction/store callback or invoke the whole route again.

Benefits: removes idle transaction during network work; durable pre-submission intent survives final UPDATE rollback. Costs: RUNNING commits before submission and survives process crashes; interrupted intent cannot distinguish never-sent from sent-with-lost-answer. Admission-to-send authorization and executor-mode transitions become separate races. Ownership changes and FOUNDATION takeover cannot be silently assigned new semantics. The implementation of `legacyQuantDenied` and its locking contract was outside this packet; this design cannot certify releasing its transaction before send as safe. A second check immediately before send alone does not close the race.

Existing deferred market hook (`request-dispatch.js:95-96`, tests `test/request-dispatch.test.js:331-344`) demonstrates post-COMMIT placement only. It is not proof that side-effectful optimize is safe there. A split needs its own typed continuation, no retries after descriptor dispatch, a defined executor-mode exclusion interval, and root-approved interpretation of durable RUNNING intent. Preserve authorization checks on reads; do not trust reusable request auth caches as authority for a new transaction. No new status/schema or lease policy is proposed in this bounded slice.

Recommendation: defer split until those contracts are explicit. If root requires continued support for >10s synchronous optimize, prefer resolving those contracts over accepting containment's latency tradeoff or raising DB timeout.
