## Owner summary

The shortest path, in plain words. Nothing runs without the owner's GO for that step.

1. **GO-P0a: a read-only look.** A read-only check of the staging host. Nothing changes.
2. **GO-P0b, GO-P1 and GO-P2: prepare and back up.** Copy the new version to the host without using it, read the database, take a backup and prove that it restores. Nothing changes for users. The owner may give these three lines in one message; they run in the order P1, P0b, P2. The backup tool for P2 can only be finished after the P0b read, so if it is not ready before the time limit of GO-P2, Root asks the owner again for GO-P2.
3. **GO-P3: a short offline migration window.** The four running staging database writers stop (the research worker is already stopped and is checked), a backup is taken, one new database table is added, and staging comes back on the old version. Expected API gap: up to about 96 seconds as in the B2 migration window, which included a backup and a cold archive of a smaller database, plus the backup time that P2 measures. Staging alerts and webhooks are not served during the gap.
4. **GO-P4: switch to the new version.** Staging is down for about 13 seconds plus one backup, then runs the new prototype.
5. **Optional GO-P5a: turn on the per-Bot performance page.** Staging is down for about 13 seconds once.

After this packet the owner can try the per-Bot QR-2 performance view (after P5a). The owner aggregate performance view and the capital-model declarations cannot be tried; they need a follow-up packet.

Once the new version has written Paper rows, a plain rollback refuses, and only a restore from backup returns staging to the old state; that restore loses every write made since that backup. The other choices then are to fix forward on the new version, or to roll the code back while keeping the new rows under the old code, each with its own GO.

## 1. Purpose and limits

### P0a read-only host preflight

One SSH session through a reviewed read-only collector. No unit, database or lasting file change; bash may keep the collector input in a private temporary file that it removes at once. P0a does not connect to the database; the inspect tools of the pin are not on the host before P1.

The collector reads the staging API environment sources under ruling D4(b): it loads only `QR2_PERFORMANCE_ENABLED`, the five research flags and `NODE_OPTIONS` (and the heap-size option in the process options and argument vector) into the host-side process memory, reports each flag as unset, 0 or 1 per source and the heap option as a boolean, and never prints, returns or stores any value, path or name. This is not a binding read. Every later fresh gate that re-reads these keys follows the same rule.

P0a records, as labels, counts, booleans, sizes and digests (never paths, names, IDs or values):

- **Host health**: available memory, free disk on the volumes that hold release trees, the database and the protected backup directory, load per CPU, running heavy jobs by class (staging and production), pending systemd reloads, any live payload of the same account, and the host boot time as a label relative to the last tracked observations (before or after 2026-10-15 and 2026-10-24 start).
- **Units, all ten staging and production roles**: active, stopped or failed; main process presence; loaded drop-in list digest and count; whether the newest layer that sets the working directory and start command is the expected one; whether the admission-off layer still sorts last on the API; the five research flags as set or unset (values 0 or 1 only); the Node major version each staging unit uses (24 required).
- **Writer restartability**, for every writer P3 stops and restarts (API, trading worker, market stream, fallback collector timer and service): whether the loaded unit is transient or persistent; whether a persistent copy exists; whether every file the start command names exists; for the stream and the collector, the file count and digest of the code directory that the loaded unit names, recorded as the baseline for P3 (ruling D14).
- **API flags and limits**: the value of `QR2_PERFORMANCE_ENABLED` from every source (unit Environment, systemd EnvironmentFile and the environment files that Node loads with `--env-file` from the start command), as unset, 0 or 1 per source, and the effective value under the precedence rule (a systemd EnvironmentFile value overrides a unit Environment value; a value in the process environment wins over a value that Node loads with `--env-file`); a boolean for any heap-size option in the process options, the argument vector or any of those environment files (`NODE_OPTIONS` loaded from an environment file reaches the QR-2 compute pool); the API unit's memory and task limits and resident memory as sizes.
- **Running revisions**: for the API and the trading worker, file-hash comparison of the tree in the working directory against the release manifests of `eb532ff`, `325d335` and `4d86822`, as a label (`EXACT_<revision>` or `OTHER`). This fixes the pair rollback target. `OTHER` for either unit stops P4 admission until Root and the owner name the rollback target.
- **Backup readiness**: presence of PostgreSQL client and server binaries of the same major version as the server; free space as in the stop conditions.
- **Ports**: whether the loopback port proposed for the P2 throwaway cluster is free; whether exactly one listener serves the staging API port and belongs to the staging API unit.
- **Protected production identities**: digest of each protected unit's identity facts, compared again after every effect phase.

**P0a stop conditions** (any one stops admission of the next phase and is reported): available memory below 2 GiB; free disk below 2 GiB plus six times the last known database size (each dump and each database copy this packet may create is counted at one times the database size: P2 dump, P2 throwaway cluster, window dump, post-migration dump, pre-switch dump, and one more for either the cold archive or an RX restore; P0a has no database connection, so this floor uses the last tracked size of 408.7 MB from about 2026-10-01, and the P2, P3 and P4 fresh gates recompute it with the P0b database size and, after P2, the measured dump size); load above 0.5 per CPU; any heavy job running; a pending reload; a live payload; any staging unit in `failed`; a writer that is transient with no persistent copy, or whose start-command files are missing, or whose named code directory is missing or unreadable (ruling D14); Node major version not 24 for the API or the trading worker; `QR2_PERFORMANCE_ENABLED` set to 1 in any source; a second listener on the API port. A heap-size option on the API, or `QR2_PERFORMANCE_ENABLED` set to 0 in a systemd EnvironmentFile (which would override the P5a layer), is not a P0a stop but blocks P5a. A unit found stopped is a fact, not a stop; it changes the GO wording (see the P4 start rule).

### P1 build, transport and inert stage

- **Build, local only.** A reviewed builder reads Git blobs of the pin (`git ls-tree -r` and `cat-file --batch` with SHA-1 recheck), writes a deterministic ustar archive (mode 0644, uid and gid 0, `release/` prefix), builds twice in memory and byte-compares, and writes outputs with exclusive create. The served list, cache tokens and auth-route set are rebuilt from the pin bytes (35 tracked files under `public/` at `4328ddc`; the served list is derived from the pin, not from that count). The dependency archive from earlier releases is reused only if a field-level equality check of the dependency fields, the lock file and the Python inputs passes against the pin; a byte check of `package.json` is not used, because its test script line changed. No `npm install` runs on the host.
- **Trees.** API tree: full tracked runtime source plus dependencies. Trading tree: as shipped by DP1S (full source tree plus dependencies), recomputed for the pin. No research tree.
- **Transport and stage.** One fresh incoming directory (mode 0700), one copy of the package files, then on the host: incoming exact, archive parsed and checked against the manifest, extraction into a partial directory with exclusive create per file, tree exact (files, bad, extra, missing), `node --check` on the server and worker entries, rename, exact again. ### P0b read-only database preflight

One SSH session through a reviewed read-only runner that first re-verifies the staged API tree exact, then runs the read-only inspect CLIs and checks of the pin from that tree. The database is read in one READ ONLY transaction per connection with no advisory lock; the reads sampled only AccessShareLock in local rehearsals. No unit, file or database change.

Two connections are used (ruling D4):

- **Migration connection.** It uses the staging migration connection selector recorded in the ignored local evidence of the B2 Window 2 precedent (D4(a)). Every later schema-owner or maintenance connection and every Paper counter reading in this packet uses the same selector.
- **Runtime-role probe.** Under D4(b) it loads only the database connection key of the staging API environment sources into the host-side tool process memory. It never prints, returns or stores a value, and returns booleans and counts only.

Neither connection is a binding read, and neither creates a binding.

P0b records, as labels, counts, booleans, sizes and digests:

- Server major version; database size; schema version; executor mode; presence of `quant_research_runs`.
- The `--inspect` state of every migration in section 5 (fence ABSENT expected, guard functions ORIGINAL, freeze ABSENT, extensions ABSENT), read as `facts.state`, not exit code.
- Table and database ACL snapshot digest of schema public, database-level ACL and database-level settings (`pg_db_role_setting`) digests, and default privileges for the schema owner. The full snapshots, including role names, stay in ignored local evidence for a possible grant replay or RX.
- The set of roles named in table ACLs, the database ACL, default privileges and object ownership, as a count and a digest (names in ignored local evidence only), for the P2 throwaway restore.
- Whether the migration connection is, or can set role to, the owner of `paper_funding`; whether the runtime role holds SELECT, INSERT and UPDATE on `paper_funding`; the effective `session_replication_role` of the runtime role in this database, and whether the runtime role may change it.
- The read-only Paper ledger check counts; queued, leased, paused or running foundation jobs and open I/O launches.
- A first reading of the Paper accounting table counters (section 8, counter rule), as a record only; the P4 baseline is taken later (ruling D11).

**P0b stop conditions:** fence already present in a shape other than INSTALLED; any guard, freeze or extension state other than the expected one; `quant_research_runs` absent; default privileges that grant the runtime role on new tables (this would make the fence ACL differ from `paper_funding` and M1 would fail; see section 11); a migration connection that cannot act as the `paper_funding` owner; a runtime role without SELECT, INSERT and UPDATE on `paper_funding`; an effective `session_replication_role` other than `origin` for the runtime role; non-zero foundation work (the owner then chooses drain or cancel under a separate decision); a staged tree that is not exact.

### P2 database backup and restore verification

P2 proves that a backup of the current staging database can be restored and measured, before any migration window is admitted. Services keep running. The restore is verified on the staging host only, which is shared with production (ruling D6).

**Admission.** P2 is admitted only when the P0a headroom passes (memory and disk floors, load at most 0.5 per CPU) and no production job is active. The P2 tool re-checks both at its fresh gate, with the disk floor recomputed from the P0b database size, compares drift under the fresh-gate rule of section 7, and stops before any effect if any check fails.

1. **Backup.** `scripts/backup-postgres.mjs` (custom-format `pg_dump`, no owner, exclusive create, mode 0600), connected through the migration connection selector of ruling D4(a) as the schema owner, never as the runtime role, to a new file in the protected backup directory on the host. The receipt keeps bytes, SHA-256 and elapsed time only. A dump runs in one consistent snapshot; it adds read load and holds AccessShareLock on every table for its duration. The dump keeps table GRANT and default-privilege entries; it does not carry roles, the database-level ACL or database-level settings, which P0b snapshots.
2. **Restore verification.** A throwaway PostgreSQL cluster of the same major version, created by the reviewed tool in a new directory it creates, run inside a transient unit with memory and CPU caps, with small memory settings and low CPU and IO priority, listening on a free loopback port only. Before the restore, the tool creates in the throwaway cluster every role in the P0b role set, as NOLOGIN, plus the runtime role (re-checked against the dump's ACL entries from `pg_restore --list`; any role named by the dump and absent from the set stops before the restore). The tool connects to the throwaway cluster only as that cluster's own local bootstrap superuser, because the pre-created roles cannot log in. The dump is restored with `pg_restore --exit-on-error --no-owner --role` set to the schema owner, so that the restore runs with the schema owner as the session role, into an empty database; never as the runtime role, never with `--data-only` or `--disable-triggers`.
3. **Checks.** Per-table row counts equal the P2 pre-dump capture within the expected live drift (tables written during the dump are reported, not failed); accounting tables fingerprinted and equal at the snapshot; schema version 14; every `--inspect` equals the source state; the read-only Paper ledger check gives the same counts. **Decryptability (ruling D7):** the tool counts successful and failed decryptions of the stored encrypted fields in the restored copy, without printing, returning or storing any value or key. Under ruling D4(b) it loads only the encryption key from the staging API environment sources into its process memory. A non-zero failure count stops. If the reviewed tool cannot do this, decryptability is reported `NOT_VERIFIED` and stays named in section 11.
4. **Removal.** The throwaway cluster is stopped, its transient unit is proved gone, and the directory the tool created in this job is removed after an exact-path proof that it is that directory. The backup file stays in the protected directory.
5. **Stop point.** Verified restore, measured dump and restore times, throwaway copy removed. Rollback: nothing on staging changed. If removal of the throwaway copy cannot be proved, stop and report; the copy holds owner data.

Restore location: the staging host only. A restore off the host, such as on the owner's workstation, is not used, because the dump holds owner data (ruling D6).

### P3 offline migration window

One window, one tool, one operations worker. P3 runs only after P1, P0b and P2 are accepted for the same pin and the R3 tool (logical path, and physical path when a cold archive is selected) is accepted. Expected API gap: quiesce of the four running writers, window dump time measured in P2, migration, and the restart with its gated manager reload; the B2 migration window kept the API down up to 96 seconds, including a backup and a cold archive of a smaller database. Adding the dump time measured in P2 keeps the estimate conservative. TradingView alerts and webhooks to staging are not served during the gap.

1. **Fresh gate.** Re-run the P0a and P0b checks under the fresh-gate drift rule of section 7, against the accepted P0a, P1, P0b and P2 records of the same pin. Environment sources are read under ruling D4(b). The disk floor is recomputed with the P0b database size and the P2 measured dump size. Any drift stops. The staged API tree is re-verified exact.
2. **Quiesce.** Stop the four running B2 writers in the B2 order: fallback collector (timer, then service), market stream, API, trading worker (ruling D3; no reduced set). Prove the research worker, the fifth B2 writer, stopped. Each stop is proved (inactive, no main process, empty control group). Zero database sessions from the stopped writers; the maintenance lock is the final gate.
3. **Window backup.** `scripts/backup-postgres.mjs` through the migration connection selector of ruling D4(a), to a new protected file; `pg_restore --list` succeeds; bytes, SHA-256 and UTC time recorded. Optional cold archive of the staging cluster (database service stopped and started, about 4 to 10 seconds in B2) if the owner selects it in GO-P3. The default is no cold archive. Choosing it adds a few seconds of database stop, a physical restore path in R3 that must be built and rehearsed first, and disk space; it allows a lossless return only before staging is used again. The data-loss window of any later restore starts at the chosen backup.
4. **Set A, offline, under the maintenance lock, with inspect before and after, every CLI run from the staged pinned tree:** `node scripts/migrate-postgres.mjs` through the migration connection selector of ruling D4(a), acting as the schema owner. Verify "PostgreSQL schema 14 ready", `scripts/paper-ledger-fence.mjs --inspect` state INSTALLED, and `has_table_privilege` SELECT, INSERT and UPDATE on the fence for the runtime role. A refusal, any state other than the expected one, or any non-pass receipt stops the window at this step: no next step, no automatic database rollback, writers stay stopped, Root reports and decides under GO-R3.
5. **Restore writers on their current code.** One gated manager reload of the persistent copies of the stopped writers (B2 rule), then restore in this order: market stream, fallback collector, API, trading worker; research worker stays stopped. Only units that were running at the fresh gate are started. The old API and the old trading worker ignore the fence and start normally on schema 14.
6. **Checks.** Each restored unit active with a new main process; API health 200 in Paper mode; trading worker heartbeat fresh; journals report no new refusal counts; protected production identities unchanged.
7. **Post-migration backup, live.** A second dump through the migration connection selector of ruling D4(a) to a new protected file after the writers are back. The dump reads one consistent snapshot, so it carries the migrated state without lengthening the gap. Bytes, SHA-256 and UTC time recorded.
8. **Stop rule for steps 5 to 7.** A writer that does not restart, a failed check, or a failed post-migration dump stops the tool. No further start attempt is made. The tool proves and reports each writer's state (running, stopped, unloaded) and the fence state. Root reports to the owner and decides under GO-R3 or a named follow-up; the window backup and the fence state still allow R3.

Stop point: writers on old code, fence installed, two new backups. The fence alone is code-rollback safe, so staging can stay in this state, but every day in this state lengthens the data-loss window of a restore from the P3 backups; P4 takes its own backup.

### P4 pair activation

Pattern: S07 x4 and DP1S S3, rebuilt for the pin. P4 runs only after P3 is accepted for the same pin and the R4, R4H and RX tools are accepted.

1. **Fresh gate.** P0a and P0b checks under the fresh-gate drift rule of section 7, against the accepted P3 record of the same pin (and the P0a, P1 and P0b facts that P3 did not change); fence INSTALLED; foundation work zero; no live payload; empty systemd job list; protected identities unchanged; `QR2_PERFORMANCE_ENABLED` not 1 in any source, read under ruling D4(b); free disk enough for the pre-switch dump and one RX copy, computed from the P0b database size and the P2 measured dump size; staged trees exact. **Retirement inventory:** every earlier once-only staging release and rollback tool namespace (S07, R7B, DP1S and S6) has its open contingency job IDs retired by a consumed marker line, so that no older tool with hard-coded layer or target constants can act on the new layout. **Startup probe:** a reviewed read-only probe from the staged API tree, run as the runtime role, calls only the schema and fence startup checks (`verifySchema`, `requirePaperLedgerFence`). Under ruling D4(b) it loads only the database connection key of the staging API environment sources into the host-side tool process memory, never prints, returns or stores a value, and returns booleans and counts only; it is not a binding read and creates no binding. Any refusal stops P4 before any unit is touched. Record a counter gate reading (section 8); it is a gate record only, not the baseline (ruling D11).
2. **Layers.** One new drop-in per unit, written as a pending file (exclusive create, 0600, fsync) and renamed in. Each layer resets and sets the working directory and start command to the staged tree; the API layer also sets `QR2_PERFORMANCE_ENABLED=0`. A unit Environment value wins over values that Node loads with `--env-file`; a systemd EnvironmentFile value overrides a unit Environment value, so P0a and every fresh gate read every EnvironmentFile and stop on 1. Nothing else changes. Its name must sort after every live layer that sets these keys, asserted against the live drop-in list, not a constant. Hazard: a name built as a fixed prefix plus the revision hex can sort before an older layer (for example `4328ddc` sorts before `4d86822`), which would leave the old tree in force and make the switch a silent no-op. The admission-off layer must still sort last on the API and still set the five research flags to 0.
3. **Switch.** Stop the trading worker and prove it; stop the API and prove it; once the database shows no session left from either stopped unit, take the **P4 counter baseline** (ruling D11; section 8) through the migration connection selector of ruling D4(a), read only in a fresh transaction; **pre-switch backup** with `scripts/backup-postgres.mjs` through the same selector to a new protected file (bytes, SHA-256, elapsed time and UTC time recorded; this backup carries the fence, suits the previous pair, and is the default RX source after P4), so that the baseline and the backup describe the same stopped state; one daemon reload; loaded-configuration gate on both units (expected drop-in list, working directory, a single start command, unchanged environment and research flags, `QR2_PERFORMANCE_ENABLED` effective 0); start the API (readiness within 40 seconds); start the trading worker (readiness). Expected API gap: about 12 to 13 seconds as in S06, S07 and R7B, plus the pre-switch dump time measured in P2. Root sets the bound before GO-P4 as 245 seconds (including an in-run rollback) plus twice the measured dump time.
4. **Start rule for stopped units.** If P0a or the fresh gate found the trading worker or the API stopped, starting it on the pin is a service start that GO-P4 must name explicitly (the suggested wording has the slot). Without that wording, P4 stops before the switch.
5. **In-run automatic rollback.** If any step fails before both pinned units pass their first readiness probe, and the Paper accounting counters still equal the P4 baseline of step 3 (taken after both old units stopped), the tool archives its own layers, reloads, and returns each unit to its P0a state (a unit that was running restarts on its previous tree; a unit that was stopped stays stopped). If the counters have moved, the tool does not roll back: it stops with both units left as they are and records `HALF_STATE` in the receipt; Root then reports, and the owner decides at the time whether to give GO-R4H (ruling D5). If any Paper table other than `signals` moved, R4H refuses, and the only paths are the R4 refusal and RX. After both units are ready, no automatic rollback; any STOP leaves both units up and a rollback needs GO-R4. A failure after the step 2 layers are in place and before the step 3 baseline exists (a failed stop or a session-wait timeout) happens before any pinned unit has started: the tool archives its layers, reloads and returns each unit to its P0a state with no counter comparison.

## 7. Execution rules (all phases)

- **One operations worker, alone.** All host steps run through the single designated operations worker, serially, outside any parallel fan-out. Root never runs a host step and never delegates GO issuance. No workflow agent, cloud agent, browser or TradingView step takes part.
- **Tool build order (ruling D9, amended).** The P0a read-only collector may be built and independently reviewed ahead of GO-P0a, as in S6. The P1 build-and-stage tool and the P0b read-only runner are built and reviewed after Root has accepted the P0a result, because P0b runs from the tree that P1 stages. The P2, P3 and P4 tools and the rollback tools R3, R4, R4H, RX and R5a are built and reviewed after Root has accepted the P0a and P0b results, because they depend on observed host and database facts. Each tool is accepted by Root before the GO it protects is admitted (rollback readiness rule below). A GO-P2 given in the same message as GO-P0b and GO-P1 is admitted only if the P2 tool is accepted before that GO's `notAfter`; otherwise Root asks the owner again.
- **Fresh-gate drift rule.** Every fresh gate (P2, P3, P4, P5a and each rollback tool) compares against the latest accepted result records of the same pin: P0a, P1 and P0b for P2; P0a, P1, P0b and P2 for P3; P3 for P4, plus the P0a, P1 and P0b facts that P3 did not change; P4 for P5a; and, for a rollback, the Root-reviewed receipt of the job it reverses (pass or stop) plus the last accepted result record before that job. Only the changes that the accepted phases in between made by design are allowed. Drift means any other change in identity and configuration facts: unit states and main processes, drop-in lists, trees, start-command files, inspect states, ACL, role-set and settings digests, flags, Node versions and protected identities. Database size and table counters move while writers run; they are re-recorded, not compared. Any drift stops before any effect.
- **Connections and environment sources (ruling D4, extended).** Every schema-owner or maintenance database connection and every Paper counter reading uses the migration connection selector of the B2 Window 2 precedent. Every read of environment sources loads only the named keys into the host-side tool process memory and returns booleans and counts only. The tools never print, return or store a value, path or name from these sources.
- **One-use manifest per job.** Each job has a fresh job ID and an immutable manifest that pins this packet, the pin, the tool code SHA-256, the allowlist SHA-256, the freshly derived host pins, the limits, the owner GO reference and a start-by time at most 10 minutes after dispatch. The manifest's execution directory must resolve to the directory the tool runs in.
- **GO freshness.** Each job runs under a Root argv GO carrying the job ID, the tool source SHA-256, `approvedAt` and `expiresAt` 120 seconds later; the approval must be at most 60 seconds old with at least 45 seconds left at the gate and again before consume. Each owner GO line carries a `notAfter` UTC time; Root does not dispatch after it. If more than 24 hours pass between an owner GO and dispatch, Root asks the owner to re-confirm the checklist first. An owner GO whose pin differs from the current pin is void (ruling D1).
- **Consume and marker.** Before any connection, the tool creates an exclusive consumed marker for the job ID (exclusive create and fsync) and appends a marker line to its plan. A consumed job ID never runs again. Each attempt carries a fresh 16-byte nonce in its phase framing. Before admission, Root searches every local checkout for an earlier attempt of the same job.
- **No retry.** No job is retried under the same GO. After a lost receipt, the next job ID of the same family waits 1335 seconds (activation family) or 1035 seconds (rollback family). Contingency job IDs exist only after a pre-effect stop with no effect.
- **Receipts.** `pass:false` always means STOP. A pass code on a non-pass receipt becomes `LOCAL_UNCONFIRMED`. Raw output stays in ignored local evidence; tracked records keep labels, counts, sizes, timestamps and verdicts only.
- **Write allowlist.** Each tool has a reviewed allowlist of host writes for its phase, proved by fakes that refuse everything else. Database writes happen only through the repository migration and rollback scripts under the maintenance lock, and, for R3 and RX, through the restore tool's reviewed fixed statements (database rename, create, restore, ACL and settings re-apply); never through ad hoc SQL. Release and rollback tools never delete, except the P2 tool's exact-path removal of its own throwaway directory; anything replaced is renamed or moved aside and kept.
- **Rollback readiness.** No effect phase is admitted before its rollback tools are built, rehearsed and accepted by Root: GO-P3 needs R3 (logical restore, and physical restore when a cold archive is selected); GO-P4 needs R4, R4H and RX with the pre-switch backup as source; GO-P5a needs R5a.
- **Limits.** Remote and local timeouts with kill-after per job; an author check asserts the worst case fits inside the remote limit minus 60 seconds. Host-health gates as in P0a, re-checked at every fresh gate.
- **Usage reserve (ruling D8).** Root reads current usage before each phase. An effect phase (P1, P2, P3, P4, P5a) is admitted only when a fresh reading shows more than 30% remaining in every known window and the phase's whole reservation, including its delayed checks and its rollback, fits within remaining minus the 3% reserve. The read-only phases P0a and P0b follow the AGENTS.md usage bands. Above 3% and up to 30%, Root admits only one rollback job (R3, R4, R4H, R5a or RX), as a single tiny task under its own owner GO; no other phase or check job starts. At or below 3%, or with all usage unknown, no job starts; Root saves a checkpoint and reports, and only the owner can change the threshold for a named continuation. Once P3 or P4 has started its effect, a band change does not interrupt the in-run sequence, its in-run delayed checks or its in-run rollback; Root admits no next phase.
- **Privacy.** No IP address, host path, unit name, user name, role name, account identifier, environment value or secret appears in tracked files, receipts or chat. Digests of private selectors stay in ignored local evidence.
- **Windows-local pitfalls.** Tools run with an explicit working directory, keep ISO timestamps as strings when PowerShell parses JSON, and hash line-feed bytes, never CRLF working copies.

## 8. Rollback

### Counter rule

The Paper accounting tables are `signals`, `fills`, `paper_funding`, `paper_cash_journal`, `paper_snapshots`, `ledger_positions`, `ledger_position_allocations`, `ledger_daily`, `ledger_streak` and `bot_sessions`. A baseline records, per table, the insert, update and delete counters, the statistics reset time, a row count and the maximum identity value where one exists, read-only. A comparison reports "rows moved" when any counter rose, any counter is below baseline, the statistics reset time changed, or a row count or maximum identity differs. A statistics reset is never read as "no new rows". Every baseline and every comparison is read through the migration connection selector of ruling D4(a), in a fresh READ ONLY transaction (cumulative statistics are cached per transaction), and, when writers were just stopped, only after their database sessions have ended.

The P4 baseline is taken in P4 step 3, after both old units are stopped and proved stopped, next to the pre-switch backup (ruling D11). The in-run rollback, R4H and R4 compare against it, so that writes by the old pair before the switch are never counted as new-version rows. The P0b reading and the P4 fresh-gate reading are records only.

### When a migration rollback is unsafe after new writes

- **Fence (M1).** Dropping it never deletes accounting rows, but the pinned API and worker refuse to start without it. Roll it back only after the code is back on the previous pair. There is no reason to drop it for a code rollback.
- **Sets B, C and D** are not applied by this packet. If applied later, M6 needs the O12 export path after any declaration row, and set D tables refuse rollback after any row, so only a forward fix or a full restore remains.
- **Code rollback after the pinned pair wrote Paper rows.** The schema is unchanged, so old code can read the rows, but the accounting rules differ (fence at every capital decision, G1 FIFO uncovered-part pricing, transaction and lease hardening). The pair rollback therefore refuses by default after new accounting rows. After readiness, the owner can then choose a forward fix, a pair rollback that explicitly accepts old code continuing on rows written under the new rules (its own GO-R4 wording), or a full restore. In a half state where a Paper table other than `signals` moved, only the R4 refusal and RX remain (ruling D5).

### Restore mechanisms (R3 and RX)

- **Logical restore.** With every writer stopped and proved, the tool connects to the maintenance database through the migration connection selector of ruling D4(a), renames the live staging database to a kept archive name (no drop), creates an empty database with the original name and owner, restores the chosen dump into it as the schema owner with `--exit-on-error --no-owner` (never data-only, never with triggers disabled), re-applies the database-level ACL and settings from the P0b snapshot, and verifies as in P2, including the decryption count of ruling D7 (a non-zero failure count stops; `NOT_VERIFIED` if the reviewed tool cannot count without exposing values), with the encryption key loaded under ruling D4(b). The existing roles stay in the cluster, so no role is created. The renamed database is kept until a separate cleanup GO and holds owner data.
- **Physical restore (cold archive, R3 only).** With every writer stopped and proved, the tool stops the database service, moves the current data directory aside (rename, no delete), restores the archive in its place, starts the service and verifies as in P2. The moved-aside directory is kept until a separate cleanup GO and holds owner data.
- **Disk.** Either path needs room for one more database copy beside the kept one; the P0a floor counts it, and every rollback tool re-checks free disk before its effect.

### Full restore and the data-loss window

A full restore (GO-RX) is never automatic and needs its own owner GO. It stops the four running B2 writers and proves the research worker stopped. After P4 it always returns the API and the trading worker to the previous trees named by P0a before the data restore: it archives the P5a layer if present, then the P4 layers, by no-clobber rename, runs one reload and the loaded-configuration gate on the previous pair. This code move has no new-rows refusal, because the restore removes those rows. Before P4 the API and the trading worker already run the previous pair, so no code move is needed. RX then restores by the logical mechanism above and restarts the writers that were running, on old code. The fence stays when the chosen backup carries it; old code ignores it. The default source after P4 is the pre-switch backup (it carries the fence and suits the previous pair). Before P4, the source is the post-migration backup or the window backup. The RX GO wording shows the chosen backup's UTC time and its age at the time of the GO.

**Data-loss window:** every write made after the chosen backup is lost by the restore: Paper signals, fills, funding and cash journal entries, sessions, audit rows, Pine Bridge records, and market bars written by the stream and the fallback collector. Market bars may be refetched from the public market-data source later under its own scope; owner and Paper rows cannot be recovered after the restore except from a later export. With the pre-switch backup, the window runs from the P4 switch until the restore stops the writers. No off-host copy of any backup exists; a loss of the host also loses the backups.

- **Backup capacity and time.** Database size, free disk, dump and restore times are unknown until P0a, P0b and P2. Kept database copies after a restore hold owner data until a separate cleanup GO. No off-host backup copy exists.
